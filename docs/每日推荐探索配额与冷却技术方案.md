# Luobo 每日推荐去同质化技术方案（探索配额 + 跨天冷却 + 收藏即时反馈）

> 状态：方案 v1.0 已定稿并实施（2026-09-23）
> 范围：**仅「今日推荐」（每日推荐）这一路**。场景 Mix / 你的最爱 / 探索发现 / AI 歌单的生成逻辑不变
> 上游文档：`docs/首页重构技术方案.md`（§4.4 融合权重、§4.5 熟悉/探索分层、§4.6 去重与多样性、§6 数据契约、§8-7 决策）
> 触发：用户 2026-09-23 反馈「今日推荐里所有歌都是已经点过喜欢的」

---

## 1. 问题与代码实证根因

### 1.1 现象

首页「今日推荐」30 首，全部是已收藏（点过喜欢）的歌，缺少未听过的新歌。

### 1.2 根因 A：每日推荐只有一路召回，没有槽位预算

- 每日推荐 = **全库按融合分排序取 Top30**，没有"必须包含 N 首未听过"的约束（`home_recommendation_service.dart:216` `dailyRecommendation` → `:181` `_selectWithDedup`）
- 融合分 `finalScore = α·行为分 + (1-α)·内容分`，α=0.7（`:164`）
- 行为分里"听过 + 喜欢"是重加分项（`recommendation_service.dart:8-26` 权重表）：
  收藏 `starBonus` 0.20、歌手亲和度 0.28、流派 0.18、歌手评分 0.11、歌曲评分 0.10、完成度 0.09、专辑 0.06、时段 0.05、播放次数 0.04 —— 亲和度类**只有听过的歌才累积得出来**
- 未听过的歌**只有一项补偿** `noveltyBonus` 0.08（`recommendation_service.dart:361`）
- ⇒ 排序天然把"听过+喜欢"顶到前 30。α=0.7 之后，未听过的歌即便内容分满分也约 0.37 分，挤不进前排

> 注：`2026-08-05` 的 §8-7 修复（全库融合分 + 未听过补足）解决的是"推不满 30 首"，代价是引入了本文的问题——补足只在**上限卡满后**才发生，不是配额。

### 1.3 根因 B：正反馈棘轮（比打分公式更关键）

- 每日推荐缓存键 = 日期 + 知识库版本（`:223`）；`refreshUserPref()` 只重建偏好向量、**不 bump 版本**（`:126`）；`clearCaches()` 仅挂在切服务器上（`main.dart:371`）
- ⇒ **今天点了喜欢，今天的推荐不变；明天重算时该歌分更高、更靠前；用户再点喜欢……** 没有探索项打破这个循环，最终单调收敛到"全是喜欢的"
- 配套的工程障碍：首页 feed 只按**曲库 id 拼串**门控（`home_v2_screen.dart:151` `_lastRandomKey`），曲库不变时即使服务内部清了缓存，feed 也不会重建

### 1.4 根因 C：分段选歌会绕过去重上限

`_selectWithDedup` 的歌手/专辑计数器是**方法内局部变量**（`:189`）。一旦把选歌拆成"熟悉槽 + 探索槽"两段，同一个歌手的上限会被各算一次（4 首而非 2 首），破坏 §4.6 的 `同歌手≤2 / 同专辑≤1`。

## 2. 大厂对标（结论先行）

| 大厂做法 | 代表 | 本方案 |
|---|---|---|
| **多路召回 → 排序 → 重排（多样性/新鲜度/冷却）** 三段式 | 通用工程范式 | ✅ 抄结构：**配额放在召回层**，不再靠排序后的去重规则兜 |
| **一个列表只承载一个意图** | Apple Music（Favorites / New Music / Get Up! / Chill / Rediscovery 各自独立货架） | ✅ 今日推荐 =「熟悉为主 + 少量新」；纯探索交给「探索发现」 |
| 熟悉 + 新按簇混合 | Spotify Daily Mix | ✅ 熟悉槽 + 探索槽 |
| 每日固定条数、保留未听过比例、另设即时反馈流 | 网易云/QQ（每日推荐 30 首日更 + 私人 FM） | ✅ 配额 + 当日固定 + 收藏即时反馈 |
| 首页货架/卡片用上下文多臂老虎机（BaRT）选，天然带探索 | Spotify | ⬜ 二期（单用户数据量支撑不了） |
| 协同过滤 / 双塔 / 矩阵分解 | Spotify Discover Weekly 召回核心 | ❌ **抄不了**：单用户自建库无群体数据 → 不在模型上加投入，只抄结构 |

## 3. 设计

### 3.1 总览：从"一路召回"改为"两路召回（配额）+ 排序 + 冷却重排"

```
全库 cachedAllSongs
   │
   ├─ ① 冷却过滤（跨天，§3.3；安全阀：过滤后不足 limit 则忽略冷却）
   │
   ├─ ② 熟悉路（_isHeard == true）  quota = limit − ⌈limit/3⌉   ─┐
   ├─ ③ 探索路（_isHeard == false） quota = ⌈limit/3⌉          ─┤ 两路 + 补足路
   │                                                            │ 共享 artist/album 计数器
   └─ ④ 补足路（不足时按融合分从全库补，保证 30 首不缺）        ─┘（§1.4 修复）
                                                                │
                                    ⑤ 全局去重 set（§4.6）→ 今日推荐 30 首 → 登记冷却
```

### 3.2 配额（解决根因 A）

- `dailyDiscoverRatio = 1/3` → `limit=30` 时 **熟悉 20 + 探索 10**
- 按**比例**给而非写死数字，`limit` 变化（含单测里的小 limit）自动缩放
- 探索槽排序仍用**融合分**，不另起机制：未听过的歌行为分 = 歌手/流派/专辑亲和度 + `noveltyBonus`，语义即"你口味半径内的新歌"
- **不复用探索发现的一跳邻居**：每日推荐在 `generateFeed` 里先跑、先占全局去重坑（`:380`），若两路都用邻居扩散会争抢同一批候选、反而拖垮「探索发现」
- 熟悉/探索两路都不足时走补足路 → 保留 §8-7 的修复成果，**不回归"推不满 30 首"**

### 3.3 跨天冷却（打断棘轮，解决"天天同一批"）

- 新增 `RecommendedHistoryStore`（`lib/services/recommended_history_store.dart`），SharedPreferences 持久化 `songId → 推荐日序号`
- 冷却窗口 `cooldownDays = 2`：
  - **当天推荐过的不冷却** —— 同一天因收藏变化重算时不会把整批换掉（关键，否则"点个喜欢换掉整个列表"）
  - **昨天/前天推荐过的冷却** —— 实际语义为"隔一天可再推"
- 每日推荐生成后把该批 30 首全部登记
- **安全阀**：冷却过滤后候选数 `< limit` 时**忽略冷却**（小库/新库/单测小数据集不会推空）
- 存储裁剪：只保留冷却窗口内的条目，避免无限增长
- 未注入 store（`history == null`）时整体跳过冷却，退化为纯配额版，不报错

### 3.4 收藏即时反馈（打破"明天才生效"）

- **触发**：收藏集合签名（`starredSongIds` 排序拼串）发生变化 → 防抖回调里 `clearCaches()` 并 `feedRevision++`
- **不触发**：纯播放 / 跳过 / 完播 → 只更新偏好向量（影响次日与探索），**不重排当日列表**
- **理由**：收藏是显式强意图，值得即时反馈；播放是隐式行为，日更列表在听歌过程中重排会造成"列表乱跳"（Apple Music / Spotify 的货架在会话内是稳定的）
- **配套**：新增 `feedRevision`，让首页能感知"服务内部缓存已失效"。原来首页只按曲库 id 拼串门控（`home_v2_screen.dart:151`），曲库不变时清缓存也没用 —— 这是本节能生效的前提

### 3.5 去重上限全局生效（修 §1.4）

`_selectWithDedup` 增加可选参数 `artistCounts` / `albumCounts`（默认仍用方法内局部变量，**既有调用行为完全不变**）；每日推荐的两路 + 补足路共享同一对计数器 → `同歌手≤2 / 同专辑≤1` 在全部 30 首范围内成立。

## 4. 数据契约与接口

| 项 | 值 |
|---|---|
| 新增文件 | `lib/services/recommended_history_store.dart` |
| 新增 prefs key | `recommended_history_v1`（JSON：`{"songId": dayIndex}`，dayIndex = 本地日序号） |
| 构造注入 | `HomeRecommendationService({..., RecommendedHistoryStore? history})`；`null` = 不启用冷却（单测默认） |
| 新增公开成员 | `HomeRecommendationService.feedRevision`、`HomeRecommendationService.dailyDiscoverRatio` / `dailyDiscoverQuota(limit)`；冷却窗口由 `RecommendedHistoryStore.cooldownDays` 持有 |
| 每日推荐 | `dailyRecommendation(...)`：熟悉 20 + 探索 10 + 补足；**当日固定（key=日期）语义不变** |
| 收藏变化 | `_onBehaviorChanged` 检出签名变化 → `clearCaches()`（`feedRevision++`） |
| 首页门控 | `home_v2_screen.dart`：`feedKey = 曲库id串 + '#' + feedRevision` |
| 导出 | `services.dart` 追加 `export 'recommended_history_store.dart';` |

## 5. 退化与安全阀

| 场景 | 行为 |
|---|---|
| 无行为（新用户/重装） | 熟悉路为空 → 探索 10 + 补足 20 = 30 首，不空 |
| 无图谱 | α=1 纯行为，配额结构不变（仅熟悉路内排序退化） |
| 曲库 < limit | 冷却安全阀忽略冷却；补足路兜底 |
| 行为数据薄（如仅 15 首听过且同歌手集中） | 熟悉路受歌手/专辑上限约束（实测只出 6 首），其余由补足路填满 |
| store 未初始化 / 注入 null | 冷却整体跳过，退化为纯配额版 |
| 同日因收藏重算 | 当日已登记的歌曲不冷却，列表只做小幅调整而非整批替换 |
