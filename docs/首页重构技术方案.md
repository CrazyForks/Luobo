> 状态：方案设计 v1.0（2026-08-05，P0-P3 完成 + UI 迭代 + P5 最近播放歌单并入，待真机验证）

## 1. 背景与目标

### 1.1 用户反馈的痛点

1. 首页推荐精度不高
2. 推荐重复多
3. 首页模式实用度不高（UI）

### 1.2 代码实证的根因

| 根因 | 证据 |
|---|---|
| 六个推荐 section 共用同一评分函数，只是 jitter 不同，内容同源 | `recommendation_service.dart:363-482`（`getPersonalizedFeed`/`getQuickPicks`/`getDiscoverMix`/`generateMixes` 全部基于 `calculateSongScore`） |
| 无跨 section 去重、无 section 内多样性约束 | `generateMixes` 各段独立取歌，无共享"已用集合" |
| 候选池只取 50 首随机歌而非全量库 | `home_screen.dart:352` 用 `libraryProvider.randomSongs`（`library_provider.dart:236`，仅 50 首）；全量在 `cachedAllSongs`（`library_provider.dart:262`） |
| 打分维度仅歌手/风格两个粗粒度标签 | 权重表 `recommendation_service.dart:8-26`，无情绪/场景/速度维度 |
| 探索层退化逻辑导致与熟悉层重叠 | `getDiscoverMix` tier3 回落（`recommendation_service.dart:414-420`） |

### 1.3 目标

- **算法对标大厂**：内容特征（知识图谱）× 用户行为 的混合推荐，含探索/利用分层、多样性约束、负反馈、冷启动退化
- **UI 向大厂对齐**：图片优先、混合布局节奏（大卡→横滑→网格）、每日推荐大卡、一键播放、继续播放回访模块
- **工程原则**：新建首页文件替换（挂载点 `main_screen.dart:43`）；算法契约先行；文档先行，用户确认后开工

## 4. 推荐算法设计

### 4.1 数据流总览

```
┌─ 知识图谱(内容侧) ─────────┐   ┌─ 用户行为(偏好侧) ──────────┐
│ SongKnowledgeCache.getAllTags │   │ RecommendationService       │
│ (songId → 8-12 标签)          │   │ (affinity/skip/rating/star) │
└───────────┬──────────────────┘   └───────────┬─────────────────┘
            ▼                                  ▼
   KnowledgeRecommendationEngine        behaviorScore
   · 倒排索引 tag→songs                 (保留评分/收藏/跳过/
   · 歌标签向量                          最近播放惩罚/完成度/时段)
   · 用户标签偏好向量 userTagPref
   · contentScore = userTagPref·vec(s)
            │                                  │
            └──────────► finalScore = α·behavior + (1-α)·content ◄─┘
                                  │
                                  ▼
                   熟悉/探索分层 → 全局去重 → 多样性上限
                                  │
                                  ▼
                   首页模块数据契约（§6）→ 新首页 UI（§5）
```

### 4.2 内容层：`KnowledgeRecommendationEngine`（新增 `lib/services/knowledge_recommendation_engine.dart`）

1. **倒排索引**：`tag → Set<songId>`，由 `getAllTags()` 构建；图谱导入/生成完成后重建（触发点见 §4.8）
2. **歌标签向量**：每首歌 = 标签集合（二值向量）
3. **歌-歌相似度**：Jaccard = |A∩B| / |A∪B|，用于探索层一跳邻居
4. **用户标签偏好向量**（核心，替代手工权重体系）：

```
userTagPref[tag] = Σ w(s)，对每个播放过的歌 s（s 含该 tag）
w(s) = 行为综合权重（收藏 +2.0 / 评分加权 / 完成度 / 播放次数，跳过衰减）
归一化到 [0,1]；复用现有 30 天半衰期衰减机制
```

5. **内容分**：`contentScore(s) = userTagPref · vec(s)`（点积后归一化）
6. **复杂度**：2674 首 × 标签数，内存 Map 毫秒级；**无需图数据库/新增依赖**

### 4.3 偏好层：`RecommendationService` 最小改造

- **候选池改全量**：`cachedAllSongs`（替代 `randomSongs`）
- `calculateSongScore`（`recommendation_service.dart:267`）**保留**：评分、收藏、跳过惩罚、recency 惩罚、完成度、时段偏好；**移除** artist/genre/album affinity 项（内容分已覆盖，避免双计）——无标签歌保留 genre fallback
- **新增只读 getter**：暴露 `_profiles` / 各 affinity 表（只读副本），供引擎取 w(s) 聚合 userTagPref
- 现有公开方法（`getPersonalizedFeed` 等）**不动**，新逻辑走新方法，保证旧首页不受影响

### 4.4 融合

```
finalScore = α·behaviorScore + (1-α)·contentScore    α=0.7（已确认：先 7:3 行为偏重保守起步；
                                                      图谱标签质量验证后调向 0.5）
退化：无图谱 → α=1（纯行为，即现状）；无行为 → 热门（`frequentAlbums` 服务端常播专辑，`library_provider.dart:773`）+ 全库探索
```

### 4.5 熟悉/探索分层

| 层 | 候选 | 排序 |
|---|---|---|
| 每日推荐 | **配额化两路召回**：熟悉路（听过的）+ 探索路（未听过的） | 熟悉槽 20 + 探索槽 10（`dailyDiscoverRatio=1/3`），两路各按 finalScore 排序；不足时按融合分从全库补足（见 `docs/每日推荐探索配额与冷却技术方案.md` §3.2） |
| 场景 Mix | 熟悉层（听过的）为主，不足时全库补足 | 场景标签过滤 + finalScore |
| 探索层（探索发现） | 未听过的歌 | ① 种子歌一跳邻居（Jaccard>0.25）② 不足时 userTagPref 前 5 标签的代表歌 |

每日推荐的候选池语义由 2026-09-23 的改造**升级**为显式配额（熟悉 20 + 探索 10），并叠加**跨天冷却**与**收藏变化即时失效**；原有「不足时按融合分从全库补足」保留为兜底，§8-7 的修复成果不回归。探索发现仍保持纯未听过，两批候选**数据源分离**，从源头消除"探索区推已听过的歌"的重复问题。

### 4.6 去重与多样性

1. **跨 section 全局去重**：生成顺序：每日推荐 → 3 个场景 Mix → 探索发现；每段完成后 songId 入全局 set，后续段排除（最重要）。AI 歌单由 LLM 独立生成，不参与本管线去重
2. **section 内上限**：同一歌手 ≤ 2 首、同一专辑 ≤ 1 首
3. **MMR**（二期）：`score' = λ·score − (1−λ)·maxSim(已选)`，先看 1+2 效果

### 4.7 场景 Mix（通勤/学习/睡前）

标签生成 prompt 已含"节奏能量/适合场景"维度（`ai_playlist_service.dart:164-179`），直接按标签过滤：

| Mix | 标签过滤 |
|---|---|
| 通勤活力 | 高能量/快节奏/运动 或 能量高 |
| 专注学习 | 纯音乐/舒缓/安静 |
| 睡前放松 | 治愈/舒缓/慢/安静，低能量优先 |

### 4.8 数据流时序

1. **启动**：`main.dart:189-231` 初始化链中，`RecommendationService.initialize` 后挂载引擎 `rebuildIndex()`（图谱已存在则建索引）
2. **播放/跳过/评分**：`trackSongPlay` 更新 affinity → 引擎增量更新 `userTagPref`（防抖）
3. **图谱导入/生成完成**：`importFromJson` / `AiKnowledgeService` 完成后 → `rebuildIndex()` + `notifyListeners`
4. **首页打开/刷新**：`generateHomeData(cachedAllSongs)` → 各模块候选 → 去重 → 返回；**每日推荐按日期缓存当日固定**（key=日期）；3 个场景 Mix 在行为数据变化时重建；**探索发现按日缓存**（key=日期，当日固定，§8-10）

### 4.9 性能

- 倒排索引构建 O(标签总数)；打分 O(候选 × 平均标签数)；全量 2674 首单次打分 < 10ms
- 大库（>1 万首）建议打分移到后台 isolate + 结果缓存（二期）

**本页特有决策**

- **分区遮罩，不用模块的 `showScrim`**（2026-09-23 用户反馈「二级页面背景不怎么流动」后修正）：
  - 模块的 `showScrim` 是**整幅** 0.42→0.70 线性暗化。离屏实测：hero 中段（y 0.42~0.60，即**唯一不压字**的区域）空间对比度被压到 **0.023**；而「看得出在流动」靠的正是对比度
  - **流动量本身不是问题**：hero 5s 像素变化 **75.6%**，还高于 Mix 卡片的 62.6%（同 seed 同色、离屏渲染实测）
  - 改为只暗化真正压字的两块（`_HeroScrim`：顶部 58% 高、端值 0.48→0.50；底部 40% 高、端值 0→0.62→0.78），中段完全放开
  - **实测结果**：中段空间对比度 **0.023 → 0.068（≈3 倍）**；白字对比度 4.09→**3.97**（标题区）/ 3.68→**3.56**（slogan 区），均在 3.0 大字号门槛之上，可读性无实质损失
- **无封面时不注入品牌色**：`imageUrl` 为空时由包内 `FluidPalette.defaultColors`（默认深色 mesh）兜底，与首页 Mix 卡回落一致；**不再回退「红→紫红」**
- **不预降渲染分辨率**：hero 面积 ≈ 全宽 × 38% 屏高、**单实例**，且滚动时随 `SliverAppBar` 折叠而收缩，暂不触发「降分辨率」杠杆（§10）；**低端安卓真机滚动帧率待验证**
- **`CollapseMode.pin` 方案已否决**：钉住后 hero 高度被压到导航栏高度，而着色器按 `uSize` 归一化 → 图案被纵向压缩成密集横条
- **未采纳 `warp` / `speed` 盲调**：实测 `warp 3.2→2.2` 可把 5s 像素变化提到 83.5%、`speed 0.27→0.40` 把 20s 提到 95.3%，但**观感无法在本地验证**，且模块文档明确「不要拿像素指标当感知判断的替代品」——留作下一步可选杠杆，见 §9

**已知的结构性限制（下一步的真因）**：着色器用 `uv = fragCoord / uSize` **归一化**采样，所以同一套图案在大面积上会被**放大**。hero 400×304 显示约 2.2×1.7 个噪声单位，Mix 卡片 178×240 显示约 2.2×3.0 个 → **hero 的特征尺度是卡片的约 2.25 倍（像素/单位）**，图案更粗、可追踪的特征更少，这是「大面积 + 归一化 uv」的固有结果，不是 bug。要真正解决需要给模块加一个**图案尺度 uniform**（`uScale`），见 §9 二期。

**验收**：`flutter analyze lib` 零 error；全量单测 **182 通过 / 5 跳过 / 0 失败**（新增 `test/widgets/song_list_screen_test.dart` 3 例：hero 用流体 + 标题/slogan/三键保留、分区遮罩（不整幅暗化）且无封面不注入品牌色、`animActive` 埋点）；**真机（含低端安卓）确认 hero 观感与滚动帧率待办**。

> 注：全量单测当前为 **182 通过 / 5 跳过 / 0 失败**（同一仓库有并行改动，数字含其新增用例）。此前那个**加载阶段就编译不过**的 `test/widgets/fluid_background_test.dart`（写于模块迁包之前，仍引用已删除的 `lib/services/cover_palette_service.dart` / `lib/widgets/fluid_background/`，并用已改名的 `FluidBackground.alignmentFor` / `CoverPaletteService`）已**被外部删除**——该模块的着色器验证目前**没有单测覆盖**，待补。

## 8. 已确认决策（2026-08-04 全部拍板）

**设计与工程 ✅**：
- 新建首页文件替换，不修改现有首页；新文件名 `home_v2_screen.dart`，旧 `home_screen.dart` 保留不删
- 设计方向 A：Apple Music「现在就听」+ liquid glass；强调红沿用 `#FA243C`；新首页独立配色 token（暗 `#1C1C1E` / 亮 `#FFFFFF`），不改全局；adaptive tint 为二期增强
- 算法与 UI 都向大厂对标；数据/算法优先于样式；文档先行，用户明确说「开始 code」才动代码

**算法契约 ✅**（用户 2026-08-04 确认"按建议来"）：
1. **融合权重 α=0.7**（行为:内容 = 7:3，保守起步；图谱质量验证后调向 0.5）
2. **探索层先"一跳邻居"**（Jaccard>0.25）；MMR 多样性二期
3. **每日推荐当日固定**（key=日期缓存，一天一变；**内存级**——同一会话内稳定，重启应用即按最新行为/图谱重新生成，不落盘）
4. **无图谱/无行为自动退化**到现有算法（α=1 / 热门+探索），新旧切换无感
5. **候选池改为全量 `cachedAllSongs`**（不再用 `randomSongs` 50 首）；大库（>1 万首）打分后台 isolate 化列为可选优化，等库变大再上
6. **`RecommendationService` 新增只读 getter**（暴露亲和度/画像），这是对现有文件的唯一侵入点，不改任何逻辑
7. **每日推荐 = 熟悉优先 + 未听过补足**（2026-08-05 确认）：全库融合分 Top30，不再"只推听过的"——重装/新用户行为数据薄且集中在少数歌手/专辑时，原「熟悉池 + 同专辑≤1」上限会推不满 30 首（实测只剩 ~10 首）。**2026-09-23 升级**为「熟悉槽 20 + 探索槽 10」的显式配额 + 跨天冷却，补足逻辑保留为兜底，见 §8-13
8. **移除首页下拉刷新**（2026-08-05 确认）：与音乐库顶部刷新按钮（`library_screen.dart:159-163`）功能重复（同一 `refreshLibraryWithFeedback`）；且首页 feed 被 `_lastFeedKey` 门控（`home_v2_screen.dart`），曲库未变且推荐服务 `feedRevision` 未变时下拉不触发推荐/图谱重建，属"安慰剂"——同步曲库统一走音乐库刷新按钮
9. **探索发现改单曲横滑网格**（2026-08-05 确认）：歌曲用横卡（`ContinuePlayingCard`）、合集用方块网格——原探索发现复用 `MixGridSection` 方块卡，与歌单/专辑方块难区分，误认成合集；布局 **4 行 × 5 = 20 首（探索发现全量）**；卡片加宽 240、**隐藏播放按钮**（`showPlayButton:false`）、歌名允许两行（`titleMaxLines:2`）、**副标题 `歌手 · 专辑`**（`subtitle` 参数，填右侧留白）——未听过的歌认歌名比播放按钮重要；按「先列后行」填充
