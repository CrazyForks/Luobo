# Luobo 音乐库艺术家页改版技术方案

> 状态：方案设计 v1.1（2026-08-05，范围收窄：仅艺术家 tab 改版，详情页增强暂缓；待 review 放行）
> 范围：音乐库-艺术家 tab 改版（方形封面网格 + 常听置顶 shelf）+ 封面解析链路。**纯客户端改动，不动 Navidrome 服务端**
> 设计约束：单用户自建媒体库（Navidrome 无艺术家图源，用户拍板纯客户端解决）；常听置顶用 App 本地播放统计；UI 对齐网易云/QQ 方形网格；向后兼容——无播放历史不显示常听 shelf，无任何封面时渐变首字母占位
> 实施进度：⬜ 未开工（待用户「开始 code」）

---

## 1. 背景与目标

### 1.1 用户反馈的痛点

1. 音乐库-艺术家 tab 样式太素：纯文字 chip 瀑布流，无封面、无视觉层次
2. Navidrome 无法获取艺术家封面（用户不清楚根因）
3. 期望新增：常听（收藏）前 3~5 位艺术家置顶/高亮，可快速选择

### 1.2 代码实证的根因

| 根因 | 证据 | 本次是否解决 |
|---|---|---|
| 艺术家 tab 是纯文字 chip，未走任何封面渲染 | `library_screen.dart:303-455`（字母分组 chip 瀑布流 + 右缘 `_ArtistScrubber`）；现有圆形封面卡 `ArtistCard`（`widgets/artist_card.dart:10`）在此 tab 完全未用 | ✅ 解决（tab 整段替换） |
| Navidrome 服务端无艺术家图源 | `ArtistArtPriority` 默认 `artist., album/artist., external`：需专辑目录 `artist.*` 文件 / `ArtistImageFolder` 集中图 / 外部 agent（deezer,lastfm,listenbrainz）/ Web UI 手动上传，用户侧均未配置 | ✅ 客户端降级（拼贴 + 渐变） |
| 客户端拿到的大图字段从未被 UI 使用 | `Artist.artistImageUrl`（`models/artist.dart:31` 解析、`library_database_service.dart:110/447/458` 落库）无任何 UI 读取；`getArtistCoverArt` 只认 `coverArt` id + 专辑封面兜底（`library_provider.dart:146-167`） | ✅ 解决（解析链路级 1） |
| 客户端被 Navidrome 按未知客户端处理（待验证） | 请求参数 `c=Musly&v=1.16.1`（`subsonic_service.dart:38-39`）；Navidrome 按客户端类型调整响应字段（OpenSubsonic 扩展可能被抑制），需 curl 实证（§7.2） | ⚠️ 验证后定；即便被抑制也不阻塞（走拼贴/渐变） |
| 客户端未调 Navidrome 的歌手简介/相似歌手端点（`getArtistInfo2`） | `subsonic_service.dart` 无该端点调用 | ❌ 暂缓（详情页增强，2026-08-05 用户决定） |

### 1.3 已确认决策（2026-08-05 用户拍板）

| 决策点 | 选择 |
|---|---|
| 封面缺失解决路线 | **纯客户端**：artistImageUrl 直链 + 2×2 专辑封面拼贴 + 渐变首字母，不动服务端 |
| 常听置顶数据口径 | **App 本地播放统计**（`RecommendationService` 亲和度/播放次数），非 Navidrome play_count |
| tab 形态 | **方形封面网格** + 字母索引（网易云/QQ 风，2×2 拼贴更自然） |
| 歌手详情页增强 | **暂缓**（本次只做 tab 改版） |

## 4. 数据层设计（算法先行）

### 4.1 常听 TopN 计算

```
输入：RecommendationService.artistAffinityView（键=歌手名，值=播放加权亲和度）
步骤：
  1. 按 affinity 降序取前 N（N=5，常量 kTopArtistsCount，可调 3~5）
  2. 过滤 affinity > 0（无历史则列表为空 → 不渲染 shelf，天然向后兼容）
  3. name → Artist 映射：cachedAllSongs/artists 建立 name→artistId 归一表，
     防同名艺人合并（服务端歌手 id 不同，名字可能相同）
  4. 结果缓存：仿 artistSongCountsCache 模式（library_provider.dart:204-210），
     随 library 变化失效，不每帧重算
```

- 暴露方式：`RecommendationService` 现有 `_getTopArtists`（`:659-666`）加只读 getter `topArtistsView(int limit)`（键为名字），归一映射放 `LibraryProvider`（持有 artists/songs 缓存）
- 备选口径：`SongProfile.playCount` 按 artistId 聚合（与听歌报告同源，`listening_report_screen.dart:318-330`）；affinity 含时间衰减，playCount 为累计——**affinity 优先，playCount 兜底**，实现时两路都算选值大者（同一 artistId）
- 不做：不改动 RecommendationService 现有键语义（避免波及首页推荐引擎）

### 4.2 封面解析链路（统一入口 `LibraryProvider.resolveArtistCover(Artist)`）

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `artist.artistImageUrl` 直链 | Navidrome 返回的 last.fm/deezer 大图 URL，字段已存库（`artist.dart:31`）从未使用；需经 `getCoverArtUrl` 同款 size 缓存逻辑 |
| 2 | `artist.coverArt` → `getCoverArtUrl` | `ar-xxx` id，Navidrome 有图时才返回 |
| 3 | 专辑封面单图 | 现有 `getArtistCoverArt`（`library_provider.dart:146-167`）保留 |
| 4 | 2×2 专辑封面拼贴 | 新增 `ArtistCollageCover`：取该艺人最多 4 张专辑封面（cachedAllAlbums 按 artistId，零网络），2×2 GridView 拼方 |
| 5 | 渐变首字母占位 | 新增 `ArtistPlaceholder`：主题色低饱和渐变 + 首字母大字（拼音分组首字母一致，视觉有归属感） |

- 图片缓存：沿用全 App 统一 `size=600` 固定请求（`getCoverArtUrl` 同 size 命中磁盘缓存，`subsonic_service.dart:500-532`）；`artistImageUrl` 为外部直链，同样交 `cached_network_image` 磁盘缓存

## 5. UI 层设计

### 5.1 音乐库-艺术家 tab（`library_screen.dart:303-455` 整段替换）

结构（自上而下）：

1. **「常听」横向 shelf**（`kTopArtistsCount` 张方形小卡：拼贴封面/占位 + 名字 + 播放次数小字，点击进详情；空则不渲染）
2. **字母分组方形网格**：`GridView` 2~4 列自适应（`SliverGridDelegateWithMaxCrossAxisExtent`，`maxCrossAxisExtent≈140`，`childAspectRatio≈0.9` 给名字留行），每项 = 方形封面（解析链路 1→5）+ 名字 + 歌曲数（`artistSongCounts`，`library_provider.dart:208`）
3. **分组头 + 右缘字母索引**：`_firstLetter` 分组头与 `_ArtistScrubber`（`:432-455`）原样保留，滚动定位逻辑（`_letterIndexMap`）按新行高重算

交互：网格卡 hover/按压出播放按钮（复用 `PressableScale`）；无封面占比高时渐变占位保证页面不素（不出现灰底墙）。

## 7. 风险与验证

### 7.1 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| `_artistAffinity` 键是名字，同名艺人合并 | 常听 shelf 可能少人/错人 | name→artistId 归一表 + 取最大 affinity 的 artistId |
| `artistImageUrl` 外部直链失效/防盗链 | 封面破图 | 走 cached_network_image 磁盘缓存 + 失败回调降级到下一级（解析链路 2→5） |
| Navidrome 对未知客户端（`c=Musly`）抑制 OpenSubsonic 字段 | `getArtists`/`getArtist` 的 `coverArt`/`artistImageUrl` 可能为空 | §7.2 实证；即便为空也不阻塞（走拼贴/渐变占位） |
| 方形网格 + 拼贴组图量大 | 列表滚动卡顿 | 拼贴只渲染 ≤4 张小图 + 统一 size=600 缓存命中；网格复用 `_coverUrlCache`（`library_screen.dart:55-61`） |

### 7.2 真机/终端验证步骤（开工前先实证封面链路）

```bash
# 服务端是否有图：直接查列表数据源 getArtists，看每 artist 的 coverArt / artistImageUrl
curl -s "http://<navidrome>:4533/rest/getArtists&u=<用户>&t=<token>&s=musly_stable&v=1.16.1&c=Musly&f=json" \
  | jq '.subsonic-response.artists.index[0].artist[0]'
```

- 返回含 `coverArt`（`ar-xxx`）/ `artistImageUrl` → 服务端有图，客户端展示链路直接用
- 两者都空 → 走拼贴 + 渐变占位（不影响本次方案成立）

- ❌ 不改首页在用的 `ArtistCard` 圆形形态（新方形卡独立文件）
- ❌ 不动 `RecommendationService` 现有键语义与首页推荐引擎
- ❌ 不做歌手搜索/排序切换（超出本次范围）
