# 局域网转码策略技术方案

> 状态：方案评审中（未开始编码）
> 日期：2026-08-06
> 相关文件：`lib/services/transcoding_service.dart`、`lib/services/subsonic_service.dart`、`lib/providers/player_provider.dart`、`lib/main.dart`、`lib/screens/settings_streaming_tab.dart`、`lib/screens/settings_mechanism_screen.dart`

## 一、背景与目标

用户只配置了 Navidrome **外网**服务器地址（未配置局域网地址），在家连 WiFi 播放时提示「不转码」。但审查发现：

- 未配置局域网地址时，`SubsonicService.resolveActiveUrl()` 直接把 `_activeBaseUrl` 钉在外网地址（`subsonic_service.dart:93-101`），**所有请求（含 `/rest/stream` 播放流）都走公网路径**，不会走局域网。
- 「不转码」提示只反映转码设置（`TranscodingService` 默认 `_enabled=false`，`transcoding_service.dart:69`），与走 LAN 还是公网**完全无关**。
- 地址选择（LAN 探测）与转码决策（WiFi/移动码率）是**两套完全解耦的逻辑**，转码档位挂的是「WiFi/移动」而不是「LAN/公网」。

用户设计初衷：**只有局域网环境才 100% 不转码**——家里局域网快、不吃家庭宽带上行；公网路径需要转码，否则大体积歌曲受限于上行带宽会卡顿。

### 目标规则（已与用户确认定稿）

1. **局域网链接（`activeBaseUrl == localUrl`）→ 一定不转码**，不看设置里的转码开关（`_enabled`）与 WiFi/移动网码率、格式。
2. **非局域网链接 → 按现有设置判断**：转码开关 + WiFi/移动网码率（smart）或手动码率（manual）。
3. **默认 `_enabled=false` 保持现状**（不改变用户已形成的设置语义）。

## 三、改动方案

### P0：TranscodingService 增加 LAN 感知（核心）

`lib/services/transcoding_service.dart`：

1. 新增字段与方法：
   ```dart
   bool Function()? _isLanOverride;
   void setLanStateSource(bool Function() isLan) => _isLanOverride = isLan;
   bool get isLanOverrideActive => _isLanOverride?.call() ?? false;
   ```
2. `currentBitRate` getter（`:81-85`）开头加：`if (_isLanOverride?.call() ?? false) return TranscodeBitrate.original;`
3. `getCurrentFormat()`（`:226-229`）开头加：`if (_isLanOverride?.call() ?? false) return null;`
4. `getCurrentBitrate()` 无需改动：`currentBitRate` 在 LAN 返回 `original(0)` 后，既有判断 `bitrate == TranscodeBitrate.original ? null : bitrate`（`:223`）自动返回 `null`。

> 语义说明：`currentBitRate` 在 LAN 返回 0、format 返回 null → 播放 URL 不拼 `maxBitRate`/`format` 参数 → Navidrome 原码直出。`_enabled` 被架空符合规则 1。

### P1：SubsonicService 切换后通知转码层刷新

`lib/services/subsonic_service.dart`：

1. 新增 `void Function()? onActiveUrlChanged;`
2. `_activeBaseUrl` 三处赋值点（`:127`、`:143`、`:183`，以及 `configure()` 中 `:57` 的置空）后调用，**仅当值发生变化时**：封装 `void _setActiveBaseUrl(String? url) { if (url == _activeBaseUrl) return; _activeBaseUrl = url; onActiveUrlChanged?.call(); }`

`lib/main.dart`（`subsonicService` 创建于 `:188`，`transcodingService` 创建于 `:266`）：

```dart
transcodingService.setLanStateSource(() => subsonicService.isUsingLocalUrl);
subsonicService.onActiveUrlChanged = transcodingService.notifyListeners;
```

> 这样设置页生效码率显示、下一首曲目 URL 决策、toast 全部随地址切换同步刷新。
> **接线顺序约束**：接线必须位于 `MultiProvider`（`main.dart:268`）之前——`AuthProvider` 在 `:286` 创建，其构造函数即触发 `_loadSavedConfig()` 的首次 `resolveActiveUrl()`。当前创建顺序（`:188` subsonicService → `:266` transcodingService → 接线 → `:268` MultiProvider）天然满足，需在实现时保持。

### P1.5：登录页 LAN-only 配置双份存储

`lib/screens/login_screen.dart`：

- 现状 `:396-400`：serverUrl 为空且 localUrl 非空 → `serverUrl = localUrl`；随后 `:415-418` `effectiveLocalUrl` 因与 serverUrl 相同被置 null → `hasLocalUrl = false` → `isUsingLocalUrl` 恒 false → **规则 1 对 LAN-only 用户永不生效**。
- 改法：LAN-only 时把该地址**同时写入 serverUrl 与 localUrl**（LAN-only 场景下跳过 `effectiveLocalUrl` 去重），使 `normalizedLocalUrl == normalizedUrl` → 无论探测结果如何 `activeBaseUrl` 恒等于 localUrl → `isUsingLocalUrl` 恒 true → 规则 1 恒生效（"只有局域网 → 一定不转码"）。
- 代价：`hasLocalUrl=true` 后网络切换监听会对同地址多一次 forceProbe ping，无害。
- 附带收益：冷启时「上次在远端 → 跳过探测」分支（`subsonic_service.dart:107-121`）因 `lastActive == normalizedUrl` 命中，**立即判定 LAN，无窗口期**。

### P2：player_provider 统一走 service 的公开语义

`lib/providers/player_provider.dart` 三处 `_transcodingService.enabled ? _transcodingService.currentBitRate : null` 替换为：

```dart
final maxBitRate = _transcodingService.getCurrentBitrate();
final format = _transcodingService.getCurrentFormat();
```

- `:1841-1847`（playSong 单曲分支）
- `:2799-2802`（gapless `_buildAudioSourceForSong`）
- `:2858-2864`（恢复路径）

> 行为等价（`getCurrentBitrate()` 在 `_enabled=false` 时返回 null，与现状一致），且与 UI/设置页共用同一事实来源，LAN 时自动得到 null → 原码。
>
> **实现附加（超出原 P2 范围，一致性的自然延伸）**：三处「是否转码」的**路由决策**（转码流走裸 AudioSource、原码流走 LockCachingAudioSource 缓存）从 `_transcodingService.enabled` 改为私有 helper `_willTranscode()`（`:1038`，判定 = `getCurrentBitrate() != null || getCurrentFormat() != null`，路由点 `:1861`、`:2819`、`:2876`）。否则 LAN 下 `enabled=true` 但实际是原码流，却走裸流分支失去 seek 缓存。**code review 修正**：判定必须含 format——「enabled + WiFi=Original + format=mp3」时服务器仍会转码成 mp3，只看 bitrate 会把转码流误送缓存路径（#170 seek 回归风险）。

### P3：设置页 UI 提示

`lib/screens/settings_streaming_tab.dart`：smart 模式「当前网络」行（`:151-180`）附近，当 `ts.isLanOverrideActive` 时显示一行提示（如「局域网连接中 · 强制原始音质（不转码）」），避免用户看到「设了 192 却生效原始」产生困惑。

新增 l10n key（`app_zh.arb` 及对应语言文件 + `flutter gen-l10n` 重新生成）：

```
"transcodingLanForceOriginal": "局域网连接中 · 强制原始音质（不转码）"
```

### P4：机制说明回写

`lib/screens/settings_mechanism_screen.dart:224` 附近机制文案补充：「局域网连接（activeBaseUrl==localUrl）时强制不转码，忽略转码设置」。

## 四、边界与取舍（自审结论）

| 边界 | 结论 |
|---|---|
| 只配外网地址 | 规则 2 生效（按设置）。用户补填局域网地址后规则 1 生效 |
| 只配局域网地址（LAN-only） | P1.5 双份存储后规则 1 恒生效（"只有局域网 → 一定不转码"），冷启立即判定 LAN |
| Jellyfin 服务端 | `isUsingLocalUrl` 对 Jellyfin 恒 false（`subsonic_service.dart` isUsingLocalUrl）：Jellyfin 的 base URL 始终是 serverUrl（`jellyfin_service.dart:32`），LAN 探测不影响其实际流量——若判为 LAN 会在 WAN 路径上强制原码（规则 1 错位），故排除，Jellyfin 恒走规则 2 |
| 冷启动窗口期（上次会话在远端 → 跳过探测，后台 3s 才切 LAN）第一首可能按远端决策 | 接受。后台探测切换本身走 P1 回调，规则 1 在切换后立即生效，仅窗口期内第一首受影响 |
| gapless 预构建 source 不随 LAN 切换重建 | 接受，与现有 smart 模式 WiFi/移动切换行为一致 |
| VPN 连回家误判为 LAN（探测通即 LAN） | 接受，无害 |
| LAN 探测失败回退公网 | 规则 2 生效按设置转码，**修掉「公网路径 + 不转码」的最差组合**（本次核心收益之一） |
| 播放中地址切换，当前已加载流不中断 | 正常，URL 已固定，只影响下一首 |
