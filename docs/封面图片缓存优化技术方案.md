## 1. 背景与目标

### 1.1 背景

v1.1.5 已落地"封面键归一 + 单尺寸 300 + 全量预热"（见《图片缓存与播放性能优化技术文档.md》），磁盘缓存压力已显著下降。但用户实际使用中**图片加载仍感觉慢**。

本轮对照 5 个主流开源 Navidrome/Subsonic 客户端（Ultrasonic / Subtracks / DSub / Amperfy / Substreamer）的封面缓存实现，结合 Luobo 源码排查，定位到 5 个具体缺口（§2.2），其中 2 个（F1/F2）直接造成"每次加载慢"，其余为缓存失效语义与参数边界问题。

### 1.2 目标

- **P0/P1**：消除"每张图首次加载都要重新握手 / 每次切歌都要冷下载高清图"的固定开销；
- **P2**：让全量预热的成果真正反映到首屏（磁盘有图 ≠ 内存有图）；
- **P3**：修正 URL 为 key 的衍生问题（换密码全失效、切歌高清图冷下载、刷新不刷封面），为多服务器/多账号场景提供正确语义；
- **P4/P5**：修正登出清缓存过激、缓存上限/过期边界。

### 1.3 设计红线

- **不推翻单尺寸 300 主链路**（已实施且解码量降 16 倍，多尺寸方案是倒退）；
- 只给"系统级消费"（Control Center/锁屏/cast）补 600 高清档，且通过缓存复用避免重复下载；
- 缓存正确性优先于缓存命中率（孤儿文件、封面不刷新、多服务器串图三类风险不引入）。

### 2.2 本轮新发现（5 个缺口）

**F1：封面下载不走 dio 连接池 —— 每次新 TCP+TLS 握手**
`CachedNetworkImage`/flutter_cache_manager 内部默认 `HttpClient`，每次下载都是新连接、无连接复用；`subsonic_service.dart` 配好的 dio 连接池/证书/超时（`subsonic_service.dart:44-45, 238-323`）对封面完全无效。自签名 HTTPS 场景还会额外付出握手/证书开销。**同类对照**：Subtracks 显式把项目 httpClient 注入 `HttpFileService`（`lib/cache/image_cache.dart`）；Substreamer 走自己的 OkHttp/URLSession（`CachedImage.tsx` 注释明确为自签服务器）。

**F2：`player_provider` 缓存查找是死代码 —— 每次切歌 Control Center 冷下载 600px**
`_refreshArtworkUrl`（`player_provider.dart:871-915`）为 iOS Now Playing/Control Center 找高质量封面：从 1200 到 200 逐档用显式 key `'${coverArtId}_natural_$sz'` / `'${coverArtId}_$sz'`（L894-907）查 `coverCacheManager`。
- 全库 grep `_natural_` 仅此一处（L895），**无任何写入方**；
- key 体系也不匹配：`coverCacheManager` 条目 key 全是 URL（`album_artwork.dart:196-197`），短 key 永远 miss。
- **实际效果**：每次切歌都走到底部 `getCoverArtUrl(coverArtId)`（size=600，L909）新请求一张 600px；列表只缓存 300px，因此大部分歌的 600 图都是**冷下载 + 服务端转码**。

**F3：全量预热只落盘、不预热内存 —— 首屏滚动实时解码**
`_preloadCoverArt` 用 `downloadFile(url)`（`library_provider.dart:883-909`）只写磁盘；UI 真正划到那张图时 `CachedNetworkImage` 仍要"读盘→解码→进 ImageCache"。全量预热使磁盘命中率上去了，但**首次滚动到该图仍有解码延迟**（300px 解码虽小，批量出现时仍卡）。

**F4：URL 为 key 的衍生问题（3 个）**
1. **换密码/换端口/换服务器地址 → 全部 key 变化 → 缓存一次性全失效**（URL 含 token，token 由密码算出，`subsonic_service.dart:354-375`）；
2. **刷新按钮不刷封面**：`refresh()`（`library_provider.dart:918-952`）只重拉数据（artists/albums API）+ 触发 `_preloadCoverArt`（命中跳过），**不 emptyCache、不重下封面**——服务端换了某张封面后，点刷新列表数据变新但封面仍显示旧缓存，唯一自动刷新窗口是 60 天 stalePeriod；
3. **无法按 id 反查缓存**：正是 F2 死代码的根因（想按 coverArtId 找缓存文件，但 key 是 URL）。

**F5：缓存边界两处**
1. **登出清缓存过激**：`auth_provider.dart:413` 登出时清空全部封面磁盘缓存。同账号登出再登回（URL 完全不变）缓存全部有效却被销毁；换账号场景 URL 含 token 天然隔离、不会串图。Navidrome 的 coverArt id 是库级共享，缓存可安全复用。
2. **1000 张上限 + 60 天 stalePeriod 的边界**：
   - 上限：服务端删歌后缓存文件成孤儿，靠 LRU 兜底淘汰——**上限不能无限制**（孤儿无出口、磁盘膨胀）；
   - stalePeriod：URL 无版本号（Navidrome `getCoverArt?id=` 返回最新图），**stalePeriod 是封面换图的唯一自动刷新窗口**——不能去掉（Navidrome issue #2200、Symfonium 论坛"封面更新不刷新"同问题）。

## 3. 同类客户端调研结论

### 3.1 对比表

| 维度 | Luobo（现状） | Ultrasonic (Coil3) | Subtracks (Flutter) | DSub (自建) | Amperfy (iOS) | Substreamer (RN) |
|------|--------------|--------------------|---------------------|-------------|----------------|-------------------|
| 缓存 key | URL（300+固定salt） | `md5(专辑目录)`+`.jpeg[.small]` | `albumArt[Thumb]-源ID-专辑ID` | `coverArtId+size` | CoreData 实体+relFilePath | `coverArtId+size`（SQLite 表） |
| 尺寸策略 | 单档 300 | 双档 大/小，小可回退大 | 双档 thumb256/原图 | 双档 小/大 | 按需 | **四级 50/150/300/600** |
| 磁盘缓存 | 1000 张/60 天 | 无上限（手动清理） | 无上限/永不过期 | 内存为主 | 持久化+可删 | SQLite+文件，可清理 |
| HTTP 栈 | 不走 dio（默认 HttpClient） | Coil 网络层 | **显式注入项目 httpClient** | 自建线程池 | 自建 DownloadManager | OkHttp/URLSession |
| 预取 | 全量预热（只落盘） | 无（仅提前初始化） | 无显式预取 | 无 | 下载队列 | Lookahead 预取 |
| 离线 | 无专门封面机制 | 钉住歌曲自动存大图 | `getFileFromCache` 直接渲染 | — | 封面持久化 | 本地 file:// 优先 |
| 坏缓存自愈 | 无 | 无 | 无 | 无 | `markErrorIfNeeded` | `reportBadCache` 删坏档重下 |

### 3.2 共性规律（5 个项目一致）

1. **尺寸分级是共识**（2~4 档），列表小图 / 播放页大图分开缓存，无一用单尺寸打天下；但 Luobo 已为单尺寸 300 付出实施成本且收益明确（解码降 16 倍），本轮只补系统级 600 档，不回退多尺寸；
2. **缓存 key 全部基于 ID 语义化**，无一依赖 URL 字符串 → 换密码/换服务器不失效、可按 id 反查；
3. **封面下载与 API 共用 HTTP 栈** → 连接池/证书复用；
4. **缓存容量大/不淘汰或可手动清**，但都有"刷新/清空"的显式入口；
5. **离线可渲染 + 坏缓存自愈**（Substreamer 最完整）。

## 4. 方案设计（P0-P5）

### P0：`coverCacheManager` 注入与 dio 同配置的 HttpClient

**问题**：F1。
**改法**：flutter_cache_manager 的 `Config.fileService` 支持注入自定义 `HttpFileService(httpClient: ...)`。新建一个与 dio 同源的 HttpClient 工厂（复用 `_configureCertificateValidation` 的证书/超时配置，`subsonic_service.dart:238-323`），注入 `coverCacheManager`。
- 改动集中在 `utils/image_cache.dart` + `subsonic_service.dart` 暴露 HttpClient 工厂；
- **影响**：所有封面下载复用连接（keep-alive）、继承自签证书/超时配置；自签名 HTTPS 场景收益最大。
**风险**：低。flutter_cache_manager 3.x `Config` 支持 `fileService`（Subtracks 已验证同款用法）。
**验收**：连续加载 50 张未缓存封面，服务端/抓包确认 TCP 连接数从 ~50 降为 1~2。

### P1：修复 `_refreshArtworkUrl` 死代码（按 URL 查缓存）

**问题**：F2（切歌 Control Center 每次冷下载 600px）。
**改法**：`player_provider.dart:894-907` 的短 key 查找改为**按 URL 查找**：用 `_subsonicService.getCoverArtUrl(coverArtId, size: sz)` 构造各档 URL，`coverCacheManager.getFileFromCache(url)` 逐档查；命中即用本地文件（`Uri.file(...)`），全 miss 才走网络兜底（保持 L909 逻辑）。
- 若 P3 落地，则改为直接按语义化 key `coverArt-<serverId>-<id>-600` 查；
- **影响**：同一首歌再次播放时 Control Center 直接复用已下载的 600 图，不再冷下载；首播行为不变（仍需下载 600）。
**风险**：低，纯读路径修复。
**验收**：切到已播放过的歌，iOS Control Center 封面瞬间出现，服务端无新增 getCoverArt 请求。

### P2：全量预热补内存预热（首屏即时解码）

**问题**：F3。
**改法**：`_preloadCoverArt` 在对首批（如前 24 个专辑 + 前 20 首歌）做 `downloadFile` 的同时，对**同一批 URL** 追加 `precacheImage(CachedNetworkImageProvider(url, cacheManager: coverCacheManager), ...)`（复用 `ImagePreloader`，`utils/image_cache.dart:32-61`）——磁盘与内存一次到位；后续批次维持只落盘。
- **影响**：首屏滚动到的封面直接命中内存，消除首次解码延迟；precache 解码发生在后台，不阻塞 UI。
**风险**：低；内存峰值可控（ImageCache 300 张/150MB 上限兜底）。
**验收**：冷启动进音乐库首屏，快速滚动无"图出现时闪一下/延迟一拍"。

### P3：语义化 cacheKey（serverId + coverArtId + size）【核心，需确认后拆子任务】

**问题**：F4（换密码全失效、无法按 id 反查、刷新不刷封面）、F2 根治。
**改法**：
1. **key 格式**：`coverArt-<serverId>-<coverArtId>-<size>`；`serverId = md5(baseUrl + username)`（不含密码——密码变化 key 不变；换账号/换服务器 key 隔离，不串图）；
2. 所有 `CachedNetworkImage` 显式传 `cacheKey`（`AlbumArtwork` 及直连点约 15 处，`grep coverCacheManager` 全量收口）；统一走 `image_cache.dart` 的 key 构造函数；
3. **迁移**：老 URL key 条目作废一次（首次升级后存量缓存重下）；可接受（用户库 3000 张内，全量预热兜底）；
4. 附带收益：
   - `_refreshArtworkUrl` 直接按语义化 key 查（P1 的终极形态）；
   - **刷新按钮可选顺带刷封面**：`refresh()` 后对"已存在但超过 N 天未更新"的封面条目 `emptyCache` 对应 key 或重新入队（默认不做，见 P4.2）；
   - 多服务器 A/B 切换（用户场景）：A 的 key 含 A 的 serverId，切回 A 缓存仍在 → 秒开；B 首次冷缓存（绕不开）。
**风险**：中——key 体系变更涉及所有调用点 + 一次存量缓存失效；需拆子任务逐处替换并验证。
**验收**：换密码后重登，已缓存封面仍命中；A/B 服务器切换不串图、切回 A 秒开；`player_provider` 按 id 查到 600 档缓存文件。

### P4：缓存失效语义修正（两个独立小改）

**P4.1 登出不再清空封面磁盘缓存**
- `auth_provider.dart:413` 移除 `coverCacheManager.emptyCache()`（或仅 `imageCache.clear()` 清内存）；
- 换账号/切服务器由 key 天然隔离（URL 含 token，或 P3 的 serverId）；
- 保留设置页手动清空（`settings_storage_tab.dart:744`）作为兜底出口。
- **验收**：误登出再登回，封面秒开；服务端无批量 getCoverArt 请求。

**P4.2 刷新按钮顺带刷封面 —— 不做（2026-08-06 拍板）**
- 现状：刷新只刷数据不刷封面（F4.2）。**保留设置页"清除全部缓存"按钮（`settings_storage_tab.dart:736-753`）作为唯一主动刷封面手段**，与 P4.2 作用重叠，故 P4.2 不做；
- 孤儿文件回收仍由 P5 的 LRU 上限兜底。

### P5：缓存参数边界（2026-08-06 更新：无上限 + 字节守护）

| 参数 | 现值 | 调整 | 理由 |
|------|------|------|------|
| `maxNrOfCacheObjects` | 1000 | **10000**（实际不驱逐） | 大库滚动永不驱逐；孤儿回收改由 `CoverCacheCleaner` 字节守护承担 |
| `stalePeriod` | 60 天 | **保留 60 天**（可拉长至 180 天，不去掉） | URL 无版本号，它是封面换图的唯一自动刷新窗口 |
| 新增 `CoverCacheCleaner` | — | 超阈值（512MB~1GB）按 `getFileInfos()` 的 `lastUsedTime` LRU 清理到阈值以下 | 对齐 `StreamingCacheCleaner`（`services/streaming_cache_cleaner.dart:9-62`）先例；设置页手清按钮（`settings_storage_tab.dart:736-753`）保留作即时手段，不依赖用户主动清 |

- **验收**：万张库滚动无驱逐；缓存目录在阈值内稳定；服务端删歌后孤儿随清理回收；换封面 ≤60 天自动更新。
